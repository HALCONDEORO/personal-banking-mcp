# Private callback data proof, synthetic only

This is a separate, one-shot data IPC proof. A real .NET child runs the existing LocalTlsRelay.ParseBrowserRequest parser. Python receives its canonical callback target over inherited standard-output pipe handles, verifies the whole transport outcome, then runs the existing ConsentAttempt.consume_callback. Only freshly generated invented callbacks are constructed by SyntheticDataRunner. Its caller cannot supply a real callback, bank, consent attempt or code. No provider call follows the returned synthetic session-body dict.

It does NOT run LocalTlsRelay, start TLS, open a socket/store, select a certificate, read a bank, sign, write a session, or expose MCP. The existing relay still forwards over its fixed HTTP loopback backend. This proof neither changes nor authenticates that existing path. The process-control fixture from the previous PR is unchanged. Production integration, including how a browser gets a truthful success/failure ACK, remains open.

## Wire and commit contract

- Python starts the fixed DataFixture.dll with a trusted, explicit absolute .NET runtime and one allowlisted synthetic mode. No shell, callback or state in arguments/environment. Child stderr is discarded. The environment and direct-child cleanup helpers are reused from relay_process; that module's implementation is unchanged.
- Request: four exact bytes PBI1, a four-byte unsigned big-endian payload length, then 1..12288 bytes of synthetic browser HTTP. Python closes stdin. The child requires exact EOF after the single input frame before calling the real relay parser.
- Output: four exact bytes PBD1, a four-byte unsigned big-endian length, then a canonical ASCII /callback? target. The Python allocation/read bound is 8192 minus the fixed origin length, matching ConsentAttempt's complete-URL limit. Neither peer allocates using an unbounded declared size. Distinct input/output magic also rejects wrong-direction frames.
- Python requires the exact one output frame, EOF with no trailing byte, child exit zero, verified direct-child cleanup, and its monotonic deadline before consuming an attempt. Duplicate frames, truncation, flood, nonzero exit even after valid data, and valid data without EOF fail without calling consume_callback. It rechecks its deadline after consumption too.
- A successful callback consumes the real in-memory attempt once. A validated denial also consumes it, but returns only a fixed error category. Other failures cancel this fixture's attempt. There is no retry on the same runner instance and no public output or exception reflecting callback values. This is not a promise about debugger locals, core dumps or a hostile same-user process.
- Cancellation during spawn waits to recover the spawned child; repeated cancellation during cleanup cannot interrupt its separate shielded cleanup task. Only after cleanup does cancellation propagate. Cleanup failure or unknown returncode forbids success. Startup and kernel cleanup can exceed the nominal timeout, as documented for the control prototype. No process-tree/Job Object containment or kernel-level hard deadline is claimed.

The trust root is the parent-created pipe handles and trusted runtime/assembly/install directory, not a named TCP port or a shared secret. There is no cryptographic peer attestation, publisher/hash verification, immutable installation, handle-security qualification on the owner's laptop, or defense against hostile code running as the same user. No listener is created by this code; platform-specific pipe implementation details are not an additional access-control guarantee. These assumptions must be resolved for the production host rather than presented as already solved authentication.

## Tests and remaining gates

The focused suite must run at least 28 tests with zero skips and a successful process exit, in normal and optimized Python. It launches actual .NET children for normal and percent-encoded success, denial, wrong state, wrong Host, malformed input/output, oversized/truncated/duplicate/trailing data, flood, nonzero exit, missing EOF, one-use and cancellation. It checks real replay rejection, no consumption before zero exit/cleanup, refusal after unverifiable cleanup or deadline expiry, value-free public tracebacks/output, fixed launch arguments/environment, and reaping of each acquired direct child. Injected failures supplement, not replace, those process tests.

The existing Windows TLS workflow builds this fixture in Release and runs both Python modes. No dependency, action pin, workflow permission, key-custody fixture or relay runtime source is changed. Relay.csproj adds only test-assembly internal visibility. Local Linux evidence is not native Windows evidence; an exact-head native workflow receipt must be inspected separately before integration.

Still needed: production relay host and private callback transport integration, browser ACK semantics, stronger Windows process/handle/custody qualification, target-laptop review, provider Production redirect support, registration, owner consent and a separately authorized live-bank adapter. No real-bank readiness or activation instructions follow from this PR.
