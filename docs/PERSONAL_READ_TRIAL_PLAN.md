# Proposed first personal read-only trial

Plan for review, 22 November 2026. **Not approved for execution.** No account is
connected by this document. The current MCP still uses invented fixtures. Do not
run a real authorization flow merely because this plan or the synthetic tests
exist. It contains no credentials, selected account identifiers or executable
activation commands. Public source does not grant access to the operator's data.

## Route and what continued access means

| Route | Official requirements | Decision for this project |
| --- | --- | --- |
| Direct Revolut Open Banking | Regulated TPP and applicable OBIE/eIDAS certificate [1] | Not a personal API-key shortcut; no new TPP/certificate enrollment under this plan |
| Enable Banking personal linked-account flow | Existing appropriately registered application, provider terms, specifically linked own accounts and separate API consent [2,3] | Intended route, subject to all unresolved gates below; not proven working for the operator |
| Revolut Business API | Different product/account scope | Not a substitute for a personal account and not used in this trial |

"Keep connected" can mean reusing a still-authorized, unexpired read-only session
between deliberate reads. It cannot mean permanent access, unlimited polling,
automatic bank login or automatic approval of new consent. A stored session can
expire or be revoked early. No always-available service or connection date is
promised.

Three lifetimes must stay separate:

- **Application JWT:** short-lived authentication generated by a trusted local
  signing bridge. It is not bank consent or a long-lived password. This repo's
  signer adapter only checks shape; its Windows backend/integration is missing.
- **Enable Banking session/consent:** the client requests `valid_until`; the actual
  ASPSP's current `maximum_consent_validity` limits it. The provider says most
  ASPSPs allow180 days, not that every Revolut account does. Use the actual
  discovery/session response and earlier local deadline. Reauthorization is
  required at expiry and can be required sooner [4].
- **Revolut internal tokens:** a dated Revolut update effective4 August2025 says
  newly issued access tokens last60 minutes; refresh tokens last180 days for EU,
  50 years for long-lived UK tokens and90 days elsewhere [5]. Enable Banking
  documents that it handles ASPSP token refresh internally. Do not copy Revolut
  refresh tokens into this repo/client or implement a second refresh loop [4].

Revolut's general FAQ still describes old long-lived access-token durations;
that wording conflicts with the dated refresh-token update. This plan follows
the specific update for direct-API token behavior, not the stale wording [5,6].
An omitted direct-API `ExpirationDateTime` is not proof of perpetual access:
token lifetime, earlier consent expiry and revocation still apply [5,7]. None of
those direct-API durations establishes the selected aggregator session lifetime.

## Scope to approve before execution

Personal account only, owned by the operator; accounts, balances and transactions
only. No payments, transfers, trading, FX, payees, cards, profile changes or
Business access. A first bounded trial should select **one account** and perform
one balance retrieval, then one short explicitly chosen transaction date range
with a fixed small page/request budget if the balance stage succeeds. The exact
account, range, page budget and consent expiry must be visible and accepted
before the real attempt. Do not silently widen the allowlist if more accounts
are returned.

This plan proposes on-demand reads, not a background schedule. Continuous or
recurring access, caching, retention and the place where private results will
be displayed need a separate reviewed design and the operator's choice. A
standing wish to read later is not evidence that the operator is present for
every automated request.

## Hard gates before the first real request

1. Verify current personal account entity/country and the matching provider
   ASPSP/personal PSU scope. Do not infer them from residence, telephone number,
   an old IBAN example or another Revolut product.
2. Verify the existing application's current environment, permitted personal
   use, exact public-certificate identity, registered redirect and linked-account
   status. No new token, permission, registration, key or trust change is
   authorized by this plan. If one is needed, stop and obtain separate approval.
3. Complete and review the trusted Windows signing/transport bridge, production
   TLS/private callback host, protocol/ACK integration, secure session lifecycle
   and real-read adapter. The current isolated fixtures do not supply these.
   [The roadmap](../ROADMAP.md) remains a release gate, not an activation toggle.
4. Qualify the intended Windows device: key custody/ACLs, trusted installation,
   process/pipe security, storage, timeout/cleanup and exact recovery. A hosted
   runner's generated keys and DPAPI tests are not target-device qualification.
5. Establish provider support for the exact Production redirect and actual
   desktop/mobile return route. Phone localhost is the phone, not the laptop.
   No public relay, tunnel, warning bypass or new trust root as a workaround.
6. Review the full consent wording, selected account set, requested expiry,
   local data retention and revocation method with the operator. Registration,
   Control Panel account linking and API consent are separate [2,3].

These gates are not yet all met. Until they are, a provider UI test, if separately
chosen and approved, is not a working test of this repository's live read path.
No account inspection or consent operation is authorized just to fill the gaps.

## Steps the operator performs, once the plan is approved and gates pass

- Start the reviewed local application on the approved device. Check its exact
  version/receipt and visible read-only scope before opening the official flow.
- Personally inspect and accept any required provider terms and bank consent;
  complete Revolut login/SCA in the official app/site on their own device. The
  current documented Ireland integration can use app switching, push/SMS or QR,
  depending on device [8]. That is a description, not a request to relay codes.
- Enter passwords, passcodes and OTPs only into the legitimate bank UI. Never
  put them in chat, a repository, a log, an issue or an assistant message. Agents
  must not receive or relay the authentication codes or private callback URL.
- Select only the intended account and inspect granted expiry/scope. Abort if
  anything differs. The callback code/state remains inside the reviewed local
  host and its private IPC, never displayed or copied out.
- If the return opens on the wrong device/browser or warns about TLS, stop.
  The operator must not paste the callback elsewhere to force the test through.

The local client's `POST /auth` and `POST /sessions` are consent/session-changing
operations even though the resulting data access is read-only. Their exact
execution must be within the approved attempt. No automatic retry after a
POST timeout or uncertain result [9].

## Bounded client read sequence, not yet implemented as a live workflow

1. Validate the private session response and authorized status, exact ASPSP,
   country, personal PSU type, chosen account allowlist and expiry. Persist only
   after the approved secure-storage path is verified. A larger account response
   does not widen scope.
2. Check session validity before each read/page; revocation can still race a
   successful check. Stop if the actual read reports expiry/revocation [4,9].
3. Retrieve the chosen account's balance once. Show it only to the operator in
   the approved private display, not in an execution receipt or screenshot.
4. If the first stage succeeds, retrieve only the chosen recent date range with
   the approved page/request budget. Continue pages sequentially only while
   deadlines/budget permit. An incomplete or exhausted budget is not complete
   history. No automatic range widening, background sync or bulk export.
5. End the attempt and close owned processes/listeners. Report success or the
   first failure category. Keeping the session is an explicit retention choice;
   it is not keeping the login UI or a callback listener open indefinitely.

### History and frequency are separate from consent expiry

Revolut documents that transactions older than90 days are available only within
the first5 minutes after authorization. Later reads are limited to the latest
90 days counted at request time [10]. This is a maximum-access boundary, not a
promise that every account yields full history in that initial window. The
trial deliberately does not rush to download all historic data.

Revolut's usage guide limits background account-information requests to4 per
24 hours **per account, endpoint and consent**. It describes exceptions for
sequential pagination, multiple accounts, the initial authorization window and
a user genuinely present and actively requesting data [11]. Its transaction
reference repeats the4-in24h limit after the first5 minutes unless the user is
present [10]. Do not treat that as4 total HTTP calls across the whole app, or as
permission for unlimited polling. Conversely, do not assume pagination is free
of all other request budgets or throttling.

For the intended aggregator route, user-presence signalling is through its
reviewed supported mechanism, not a fabricated client IP or a direct-Revolut
header pasted into the wrong API. Enable Banking exposes PSU context headers
and says bank background limits still apply [9,12]. No background schedule is
started by this first-trial plan. Stop on429; do not test the limit by retrying.

## What is stored and where

| Material | Intended approved location | Not allowed |
| --- | --- | --- |
| Bank login, passcode, OTP | Operator's legitimate bank app/site only | Chat, agents, repo, logs, local fixture config |
| Application signing private key | Existing reviewed nonexportable Windows key store on the operator's device | Repo, vault export to an agent, shell arguments, temporary PEM/token files |
| Short application JWT | Memory inside the trusted local signing/read transport only | stdout, URL, exception, screenshot or persistent debug cache |
| Callback code and state | One-use local attempt/private IPC memory, discarded after outcome | Browser-history copying, chat, public issue, output logs or retry files |
| Session ID, allowlist and expiry metadata | Operator-local current-user protected storage with reviewed path/ACL, lifecycle, recovery and deletion | Public repo, CI, general notes or unqualified plaintext file |
| Returned balances/movements | Approved private on-device display; no persistent transaction cache in the first trial | Public screenshots, PR attachments, telemetry, cloud-model ingestion by default |

`windows_private_store.py` is an isolated DPAPI component, not proof that this
integrated storage policy is implemented or that inherited ACLs/backup exposure
are safe. The exact device path and deletion/recovery behavior must be fixed and
reviewed locally before use. Do not invent a path or claim the existing POSIX
store supports Windows. No new vault token or secret request follows from this
document. Financial data sent through an MCP client can reach its model provider;
that disclosure must be reviewed before enabling real-data MCP tools.

## Minimal receipt, no financial or secret data

Record UTC/local start/end time, random non-account trial ID, code commit/tree,
platform/runtime versions, stage, fixed PASS/FAIL category, request/page counts,
cleanup result and whether the attempt ended with known or uncertain outcome.
A private boolean can record that scope/expiry checks passed; no raw response
is needed. Keep the receipt local/private unless a separate disclosure is
approved. A public CI receipt must stay fully synthetic.

Exclude bank/customer names, account/IBAN digits and IDs, balance/amount/currency,
transaction descriptions/dates, session IDs, callback URL/code/state, JWT,
refresh token, private key, auth headers, raw response/error bodies and private
paths. Generic failure categories do not authorize retaining untrusted provider
messages. Correlate locally with opaque IDs, not hashes of account identifiers.

## Renewal, revocation and the first-failure rule

- Before expiry, notify the operator and ask them to renew through the supported
  official bank flow. Never silently reauthorize or widen accounts/permissions.
  No separate client-managed Revolut token refresh is needed on the aggregator
  route [4]. Do not create extra sessions merely to extend access; they can
  invalidate an earlier one.
- Stop at the first failure: wrong account/scope/entity, unexpected permission,
  TLS/browser-return mismatch, private value in output, unsafe storage, expired
  or revoked session, invalid response/provenance, timeout,429 or challenge.
  Do not retry automatically, switch API/product or request a larger scope.
- A timeout after session creation can leave remote state. Mark it uncertain;
  do not manufacture a second attempt or tell the operator nothing happened.
- The operator may revoke using the provider's documented consent-management
  page or bank controls after the exact route is verified. API session deletion
  is a separate change requiring agreed scope. Enable Banking says it closes
  bank consent automatically **if possible**, not unconditionally [9,13].
- Deleting local session storage or stopping the app is not proof of bank-side
  revocation. Confirm each result separately. If access is retained, reads remain
  bounded by consent, expiry, account scope and bank/provider availability.

## Candidate ideas from existing implementations

See [the pinned repository review](RELATED_BANKING_IMPLEMENTATIONS.md) for six
projects, their observed licenses, source links and exclusions. No code was
copied or installed. A project advertising a live connector is not evidence
that this project's Windows custody or provider redirect works.

Adopt these as design requirements for later reviewed code, not enabled features:

- Deny by default. Grant only the named local caller, selected account set and
  read-only tools; keep consent/admin capabilities outside MCP. Missing,
  malformed, expired or conflicting policy denies access.
- A local expiry notice when the stored actual expiry is within14 days, without
  fetching bank data merely to calculate days left. Shorter consent can warn
  immediately; expired/revoked consent stops reads. No automatic reauthorization
  or external push service is enabled by this idea.
- Consider a60-minute local data cache only after the operator approves location,
  retention and stale-data behavior. Label source/observation time, retain exact
  account/currency/range identity, and never serve cached data to bypass scope,
  revocation or expiry. A60-minute TTL is not permission to fetch24 times a day.
  First trial remains no persistent financial cache.
- For any separately approved background mode, enforce at most4 bank-read
  refreshes per rolling24 hours per selected account/endpoint/consent, with a
  durable private budget across restarts and single-flight/coalesced requests.
  Reuse approved cached data instead of fetching on each question. Pagination,
  genuine user presence and initial-window exceptions require explicit reviewed
  accounting; do not use them to evade the conservative budget by default.
  No background scheduler is started here.

Do not import payment tools, public callback hosting, browser-generated/exportable
keys, automatic registration, cloud telemetry or remote caches from examples.
Reimplement only reviewed generic ideas in original code; inspect file-level
licenses and preserve notices before any future source adaptation.
